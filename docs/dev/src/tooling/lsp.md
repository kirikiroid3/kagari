# Language Server and Editors

Editor support has three parts with different jobs:

| Part | Job | Source of truth for |
| ---- | --- | ------------------- |
| `kagari-lsp` (run by `kagari lsp`) | Semantic features over LSP: diagnostics, formatting, go to definition, hover, document symbols | Meaning (it runs the real compiler) |
| `tree-sitter-kagari` | An approximate, error-tolerant grammar for highlighting, brackets, indentation and outlines | Nothing; it follows `kagari-syntax` |
| `zed-kagari` | Zed extension: wires the grammar, query files and `kagari lsp` together | Zed integration only |
| `mdbook-kagari` (run by `mdbook build`) | Highlights the Develop Guide's Kagari code with the grammar and `highlights.scm` | Nothing; it reuses the grammar and the queries |
| `textmate-kagari` | The canonical TextMate grammar (Shiki); the documentation site highlights with a copy of it | Nothing; it follows the tree-sitter grammar and `highlights.scm` |

Other editors can use `kagari lsp` with any generic LSP client, plus the tree-sitter grammar if
they support it. The user-facing setup is in the Reference's
[Editor Support](https://kagari.suitsu31.club/en/reference/tools/editors/).

## The language server

### Threads and the main loop

The server uses `lsp-server` (the rust-analyzer transport) and `lsp-types`. `run_stdio` creates a
`Connection` whose stdin reader and stdout writer threads talk to the main loop through
`crossbeam-channel` channels. `run(connection)` is transport-agnostic; the tests use
`Connection::memory()`.

`server::run`:

1. `connection.initialize(capabilities)` performs the handshake. Capabilities: full text sync
   (`TextDocumentSyncKind::FULL`), hover, definition, document formatting, document symbols.
2. Builds `Server { sender, db: RootDatabase::new(Arc::new(OsFileSystem)), projects, open,
   published, roots, shown_errors }`. `roots` are the workspace folders (or `rootUri` for clients
   without folders).
3. If the client supports dynamic registration of `workspace/didChangeWatchedFiles`, registers
   watchers for `**/*.{kis,kix}` (all events), `**/kagari.toml` (all events) and `**/*` (create
   and delete only, for assets).
4. Loads projects, publishes initial diagnostics, then loops over `connection.receiver`:
   - requests: `handle_shutdown` first; otherwise `requests::dispatch`, answered synchronously on
     the main thread;
   - notifications: `notifications::dispatch(&mut server, …)`;
   - responses (to the watcher registration): ignored.

The main thread is the only writer of the database. Requests read it in place; they are fast
because they only touch memoized queries (see [IDE Layer](../compiler/ide.md)).

### Projects

`projects.rs` keeps `Vec<LoadedProject { project: kagari_project::Project, program: Program }>`:

- `load_projects()` clears everything and loads one project per workspace folder that has a
  `kagari.toml` directly in it, then, for each open document, `find_project`.
- `find_project(file)` does nothing if a loaded project's root contains the file; otherwise it runs
  `Project::find(file's directory)`. `NotFound` is silent (the file is "loose"); other errors
  (invalid manifest, toolchain mismatch) are shown once via `window/showMessage` until the next
  reload.
- `project_for(path)` is the loaded project with the deepest root containing the path, so nested
  projects work.

A project's `Program` comes from `Project::program(&db)`, exactly as in the CLI, so the editor
and `kagari check` agree.

### Document sync

The database is the single store of text. `RootDatabase` reads a file from disk the first time a
query asks for it; after that, only explicit writes change it.

| Event | Action |
| ----- | ------ |
| `didOpen` (`.kis`/`.kix` only) | `find_project`; `db.set_file_text(path, text)`; remember in `open`; refresh |
| `didChange` | Take the **last** content change (full sync, so it is the whole text); same as open |
| `didClose` | Forget the editor text; reset the database text to the disk contents; if the file belongs to no loaded program, publish an empty list for it; refresh |
| `didChangeWatchedFiles` | `kagari.toml` changed → reload all projects. Source changed and not open → re-read it from disk. Another file under a project's asset dir → `db.set_asset_exists(path, exists)`. Then refresh |
| `didSave` and others | Ignored (the text is already synced) |

Paths are canonicalized (`uri_to_path`), so a file reached through a symlink has one identity.
Malformed notification params are logged to stderr and skipped; they are not fatal.

### Diagnostics

`diagnostics::refresh(&server)` runs after every write. It clones the database (a cheap salsa
snapshot handle), copies the program list and the open texts, and spawns a thread that:

1. runs `kagari_lang::check(db, program)` for every loaded project and converts the results
   (`code` as a string such as `E2001`, `source: "kagari"`, related information for disk files,
   std diagnostics dropped; see [IDE Layer](../compiler/ide.md#diagnostics));
2. for every open file that is in no program, parses it with `kagari_syntax::parse` and reports
   its syntax errors only;
3. publishes one `textDocument/publishDiagnostics` per file with diagnostics, plus an empty one
   for every file that had diagnostics in the previous publication (`published` set), then
   replaces the set.

The whole computation runs inside `salsa::Cancelled::catch`. The next database write on the main
thread cancels a running computation (salsa unwinds it with `Cancelled`; nothing is published).
A thread that has finished computing still holds its database clone while it publishes, so the
next write waits for it; publications therefore never arrive out of order. `check` includes
stage 5 analysis, which can be slow on a large story; cancellation is what keeps typing
responsive.

### Requests

`requests::dispatch` maps a method to a `fn(&Server, Value) -> Result<Value, serde_json::Error>`
and wraps the call in `catch_unwind`: a panicking handler logs to stderr and returns
`InternalError` instead of taking the server down. Unknown methods get `MethodNotFound`; bad
params get `InvalidParams`. Every handler returns `null` when it has no answer (outside a project,
no reference at the position).

| Request | Implementation |
| ------- | -------------- |
| `textDocument/formatting` | `kagari_fmt::format(db text, kind)`; one `TextEdit` replacing the whole document, or `null` if unchanged or not formattable. The client's `FormattingOptions` are ignored: the layout is fixed |
| `textDocument/definition` | `locate` (project program, `SourceFile`, byte offset) → `ide::definition` → `Location`; std targets are materialized first |
| `textDocument/hover` | `ide::hover`; Markdown content and the reference's range |
| `textDocument/documentSymbol` | `ide::file_symbols` → nested `DocumentSymbol`s; works for loose files too |

`LineIndex` converts between byte offsets and LSP positions. LSP columns count UTF-16 code
units, which matters for Japanese text: `position` counts `encode_utf16` units from the line
start, and `offset` walks chars adding `len_utf16`. A column past the end of a line clamps to the
line end (before `\r\n`); a line past the end of the text has no offset.

### Std files

Std declarations are embedded in `kagari-std` and have `FilePath::Std` identities. To let the
editor open a definition in std, `std_files::materialize(name)` writes the file to
`$TMPDIR/kagari-std-<TOOLCHAIN_VERSION>/<name>` when it does not exist yet and returns that path.
The directory is keyed by version only, so during development (when the std changes without a
version bump) a stale copy can be shown; delete the directory to refresh it. The materialized
file is a loose file to the server: opening it gives syntax diagnostics only.

### Tests

`tooling/kagari-lsp/tests/lsp.rs` writes a project into a temp dir, runs `kagari_lsp::run` on a
thread over `Connection::memory()`, and drives one scenario: open a file with a type error (an
`E2…` diagnostic is published), fix it (diagnostics cleared), hover (header and doc comment),
go to definition, document symbols, formatting, then `shutdown`/`exit`. The client helper skips
unrelated messages and waits up to 60 s per message. `line_index/tests.rs` covers the position
conversions. Run `cargo test -p kagari-lsp`.

## Tree-sitter grammar

`tooling/tree-sitter-kagari/grammar.js` is derived from tree-sitter-rust's grammar (MIT; the
header keeps the attribution) and cut down to Kagari. It exists for editors, not for the
compiler: it must accept every valid program and degrade gracefully on invalid ones, but it does
not need to reject anything. The header lists where it is deliberately more permissive than the
compiler:

- forms (`name!(…)`, `name![…]`, `name!{…}`) hold attributes, arms and expressions separated by
  optional commas, in both `.kis` and `.kix`;
- `t![…]` text has no rule of its own; its strings, rubies, effects and interpolations parse as
  juxtaposed expressions (see `test/corpus/forms.txt`);
- block comments do not nest;
- invalid string escapes are accepted.

The authority is `kagari-syntax`: the lexer in `core/kagari-syntax/src/lex/mod.rs` and the
parser in `core/kagari-syntax/src/cst/parser/*.rs`. The grammar mirrors it in:

| Grammar | Must match |
| ------- | ---------- |
| `PREC` table | The binding powers in `cst/parser/exprs.rs` |
| `KEYWORDS`, `primitiveTypes`, contextual `pushdown` / `scene` | The lexer's keywords and the parser's contextual keywords |
| `TOKEN_TREE_PUNCTUATION` | The punctuation the lexer produces (for attribute token trees) |
| Item, type, pattern and expression rules | The parser's productions |
| `line_comment`, `doc_comment` (`///`, `//!`), `block_comment` | Comment lexing; `doc_comment` drives `@comment.doc` |

### Generated files

`tree-sitter generate` turns `grammar.js` into `src/parser.c`, `src/grammar.json` and
`src/node-types.json`, and copies the runtime headers into `src/tree_sitter/`. These are
committed, because consumers such as Zed compile the grammar from the repository at a pinned
revision without running the generator. `.gitattributes` marks the three generated files
`linguist-generated` and the headers `linguist-vendored`, so they are collapsed in diffs and left
out of language statistics. Never edit them by hand. The committed parser is ABI version 15
(`LANGUAGE_VERSION` in `parser.c`), so a tree-sitter CLI of a version that emits ABI 15 is needed
to regenerate it without churn. `tree-sitter.json` disables every binding (`c`, `go`, `node`,
`python`, `rust`, `swift`), so `generate` writes no binding scaffolding. `node_modules/`,
`build/`, `*.wasm` and `*.so` are ignored.

### Regenerating

The tree-sitter CLI is not part of the Nix dev shell or the Cargo workspace; install it
separately (`cargo install tree-sitter-cli` or `npm i -g tree-sitter-cli`). Then:

```sh
cd tooling/tree-sitter-kagari
tree-sitter generate      # rewrites src/parser.c, src/grammar.json, src/node-types.json
tree-sitter test          # runs test/corpus/*.txt
tree-sitter parse ../../example/test_game1/src/main.kis   # spot-check a real file
```

Commit `grammar.js`, the regenerated `src/` files and any corpus changes together.

Corpus files use the standard format: a `===` header with the test name, the source, a `---`
line, then the expected S-expression. Add a case for every new construct; `tree-sitter test
--update` rewrites expectations, which you must then review.

## The Zed extension

`tooling/zed-kagari` is a standalone crate (`crate-type = ["cdylib"]`, compiled to WebAssembly by
Zed) with its own `[workspace]` table and `Cargo.lock`. The root `Cargo.toml` lists it under
`exclude`, so `cargo build`/`test` at the root never builds it and its `zed_extension_api`
dependency does not enter the workspace lock file.

- **Grammar.** `extension.toml` references the grammar by Git: `[grammars.kagari]` with
  `repository`, a pinned `rev` (a commit hash) and `path = "tooling/tree-sitter-kagari"`. Zed
  clones that revision and compiles the committed `src/parser.c`. A grammar change therefore
  reaches Zed only after it is committed and pushed **and** `rev` is updated to that commit.
- **Queries.** `languages/kagari/` holds `config.toml` (name `Kagari`, `grammar = "kagari"`,
  suffixes `kis`/`kix`, line comments, `tab_size = 4`, brackets) and the queries
  `highlights.scm`, `outline.scm`, `indents.scm`, `brackets.scm`. They name grammar nodes and
  fields (`function_item name:`, `form_expression`, `form_attribute`, `doc_comment`…), so renaming
  a node in `grammar.js` requires updating them. In `highlights.scm` the last matching pattern
  wins, so general patterns come first. The books are highlighted with the same `highlights.scm`
  ([Documentation](../process/docs.md#code-highlighting)); a capture name the books should color
  needs a class in `class_of` in `tooling/mdbook-kagari/src/highlight.rs`.
- **Language server.** `[language_servers.kagari]` declares the server for language `Kagari`.
  `src/lib.rs` implements `language_server_command`: the binary is `lsp.kagari.binary.path` from
  the user's Zed settings, else `kagari` found on the worktree's `PATH`; arguments default to
  `["lsp"]` (overridable through `lsp.kagari.binary.arguments`); the environment is the
  worktree's shell environment. Without a binary it fails with a message suggesting
  `cargo install --path tooling/kagari-cli`.

To try local changes, use Zed's "Install Dev Extension" on `tooling/zed-kagari`. `/target/`,
`/extension.wasm` and `/grammars/` (Zed's grammar checkout) are ignored.

## Invariants

- The language server and the CLI see the same program for the same project: both use
  `kagari_project::Project` and `Project::program`.
- Only the main thread writes the database; every write is followed by `diagnostics::refresh`.
  Background work must run inside `salsa::Cancelled::catch` and must not hold a database clone
  longer than needed, or writes block.
- Handlers never panic the server (requests are under `catch_unwind`; notifications skip bad
  params). Only transport failures (`LspError`) end it.
- Positions sent to the client are UTF-16 based, computed from the same text the database holds.
- Every file that got diagnostics gets an empty publication once it has none.
- The tree-sitter grammar accepts everything `kagari-syntax` accepts. Generated grammar files are
  only ever produced by `tree-sitter generate` from the committed `grammar.js`.
- `zed-kagari` stays out of the Cargo workspace.

## When you change this

- **New syntax in `kagari-syntax`**: update `grammar.js` (and `PREC`/`KEYWORDS` if relevant),
  regenerate, add a corpus case, update the Zed queries if new node kinds should be highlighted or
  outlined, update the TextMate grammar `tooling/textmate-kagari/kagari.tmLanguage.json` (and its
  copy in `docs/site/grammars/` once the site documents the syntax;
  [Code highlighting](../process/docs.md#code-highlighting)),
  and update the formatter ([Formatter](./fmt.md)). Commit, then bump `rev` in
  `tooling/zed-kagari/extension.toml` to the grammar commit.
- **New LSP feature**: add the query in `kagari-lang/src/ide` ([IDE Layer](../compiler/ide.md)),
  the handler in `server/requests.rs` (or `notifications.rs`), the capability in
  `server/mod.rs`, a step in `tests/lsp.rs`, and the feature list in the Reference's
  [Editor Support](https://kagari.suitsu31.club/en/reference/tools/editors/) (en and ja).
- **New watched file kind** (a new manifest-like file): extend `register_watchers` and
  `did_change_watched_files`.
- **Changing how the Zed extension finds or starts the server**: update the Reference editor page
  (en and ja), which documents `lsp.kagari.binary.path`.
- Verify with `cargo test -p kagari-lsp -p kagari-lang`; for the grammar, `tree-sitter test` in
  `tooling/tree-sitter-kagari`.
