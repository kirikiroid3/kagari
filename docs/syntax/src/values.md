# Values, References and Closures

*Tentative.* This chapter fixes the memory model. It is simpler than Rust's on purpose: no
lifetimes and no borrow checker, at the price of references that cannot be stored.

## Value semantics

Every type is a value type. Assignment, passing an argument and returning copy the value; changing
the copy never changes the original. An implementation may share storage and copy on write, but
the program cannot observe it.

There are no moves and no destructors. A value is gone when nothing holds it.

## References are second-class

`&T` and `&mut T` exist so that a function can read or change a value the caller owns without a
copy, as `render` functions do with the screen:

```kis
const fn hanako_jumps(mut screen: Screen) -> Screen {
    screen.entity(HANAKO).cord.apply_animation(jump(20));
    screen
}
```

A reference is **second-class**: it can be passed down, never kept.

- A reference type may appear only as the type of a parameter, including a method receiver
  (`&self`, `&mut self`).
- A function may return a reference only if its receiver is a reference. The result is a
  *projection* of the receiver, a part of it, and lives until the end of the statement that
  produced it. This is what makes `screen.entity(HANAKO).cord.apply_animation(…)` work:
  `entity` projects an entity out of the screen, `.cord` a component out of the entity, and
  `apply_animation` changes it in place.
- A reference cannot be stored in a field, a local, a static or a collection, and cannot be
  captured by a closure.
- **Exclusivity.** In one call, a place passed as `&mut` may not also be passed as any other
  argument, so two parameters never alias when one of them can change.

Because a reference can never outlive the call it was passed to, a function that takes `&mut x`
behaves exactly as if it received a copy of `x` and the caller stored the result back on return.
This is what keeps references harmless for the [narrative analyses](./kinds.md#why-this-works):
a `&mut` argument of a `pushdown fn` is an in-out parameter of a finite type.

## Closures

```kis
let open_config = || nav::call(Config);
```

A closure captures by value: it copies the variables it uses when it is created. Changing a
captured copy inside the closure does not change the original; shared mutable state goes through
`&mut` parameters, story variables, or [signals](./system.md#components-and-signals).

What may be done with a closure depends on the kind of the function that creates it:

| Kind          | Closures are | May be |
| ------------- | ------------ | ------ |
| `fn`          | first-class  | stored, returned, put into elements (UI handlers) |
| `const fn`    | first-class  | stored, returned |
| `pushdown fn` | second-class | passed as an argument and called; never stored, returned or captured |

A first-class closure in the story would let story state contain closures that contain closures,
without bound. That is a higher-order pushdown system: still decidable, but the cost of analysis
grows by an exponential with each order (Ong, *On model-checking trees generated by higher-order
recursion schemes*, LICS 2006). A second-class closure is a function plus finite captured values
that disappear when the call returns, so the story stays an ordinary pushdown system.

### Closure and pointer types

Function pointer types and closure types carry the [kind](./kinds.md) of the code they call:

| Type | Holds |
| ---- | ----- |
| `fn(A) -> B`, `pushdown fn(A) -> B`, `const fn(A) -> B` | A named function of that kind |
| `Fn(A) -> B`, `pushdown Fn(A) -> B`, `const Fn(A) -> B` | A closure or function of that kind (*tentative* syntax) |

A closure that captures nothing coerces to a function pointer of the same kind; this is how a
render is written inline (see [Presentation](./presentation.md#inline-renders)). A function
pointer coerces to the closure type of the same kind.
