Kagari は、物語に関する問いにコンパイラが確実に答えられるように作られています。実際にプレイして確かめるのではなく、解析によって答えを出します。この章では、普通のスクリプト言語ではなぜそれができないのか、Kagari はどうやってそれを可能にしているのか、そして制作者が何を得て、何と引き換えにするのかを説明します。

## 制作者が確かめたいこと {#the-questions-a-studio-asks}

ビジュアルノベルの「正しい動き」は作者の頭の中にしかありません。ある台詞がどのルートのものか、あるシーンではどのフラグが立っていなければならないか、2 つの分岐が合流したあとにどの立ち絵が出ているべきか。こうした知識にかかわるバグは、作者以外には見えません。リリース前に、制作者は次のような問いの答えを知りたいはずです。

- このエンディングにそもそも到達できるか。ミオに会わずに到達できてしまわないか。
- 選択肢が 1 つも表示されない選択に行き着いて、先へ進めなくなることはないか。
- どのルートからもたどり着けないシーンや台詞はないか。
- 屋上ルートと教室ルートが合流したあと、次の台詞ではどの経路から来ても作者の意図した背景が表示されるか。
- クリックとクリックの間に動くコードは、必ず終わるか。
- パッチを当てたあとも、すべてのセーブをロードできるか。できないなら、どこで食い違うのか。

テストで答えが得られるのは、誰かが実際にプレイした経路についてだけです。*すべての* 経路について答えるには、プログラムを解析する必要があります。

## Rice の定理 {#rices-theorem}

チューリング完全な言語では、そのような解析は原理的に作れません。**Rice の定理**（1953 年）によれば、プログラムの非自明な意味的性質はすべて決定不能です。*意味的* な性質とは、ソースの見た目ではなく、プログラムが何をするかに関する性質のことです。*非自明* とは、その性質を満たすプログラムと満たさないプログラムの両方が存在することを指します。このような性質については、任意のプログラムがそれを満たすかどうかを判定するアルゴリズムは存在しません。

先ほどの問いは、どれもこの種類に当てはまります。いずれの問いにも停止性問題を埋め込めるからです。止まるかどうか分からない計算のあとにエンディングを置けば、「このエンディングに到達できるか」は「この計算は停止するか」と同じ問いになります。「クリックとクリックの間のコードは終わるか」に至っては、停止性問題 *そのもの* です。このため、物語の中で任意のコードを実行できるエンジンでは、どんなツールも、諦めるか、推測するか、一部の経路をテストするしかありません。これは工夫で乗り越えられる問題ではなく、定理です。

## 決定不能性はスタックではなくデータから生じる {#data-not-stack}

Rice の定理が当てはまるのは、チューリング完全なプログラムです。抜け道は、チューリング完全ではないものの、物語を書くには十分な表現力をもつ言語で物語を書くことです。問題は、どこを制限するかです。

- **コールスタックだけなら問題ありません。** プッシュダウンシステム（非有界なコールスタックを備えた有限状態機械）の到達可能性は決定可能で、システムの大きさに対して多項式時間で計算できます。シーンからシーンを呼んでも、再帰しても、呼び出し元へ戻ってもかまいません。
- **問題になるのは非有界なデータです。** 条件ジャンプ付きの非有界なカウンタが 2 つあるだけで、スタックがなくてもチューリング完全な Minsky 機械になります。いくらでも大きくなる整数、リスト、文字列は、どれもこうしたカウンタを持ち込んでしまいます。

そこで Kagari は、制御ではなくデータを制限します。物語では再帰、ループ、ハブマップ、共通のサブシーンを自由に使えます。そのかわり、物語が扱う値はすべて有限集合の中に収まります。

## Kagari が定理をかわす方法 {#how-kagari-sidesteps-the-theorem}

Kagari は Rice の定理に反しているわけではありません。制作者が確かめたい問いを、決定可能な部分についてしか問わずに済むようにプログラムを構成し、答えがそれ以外の部分に左右されないようにしています。これを支えるのが次の 3 つの規則です。コンパイラは 3 つすべてを検査し、違反は警告ではなくコンパイルエラーになります。

### 物語は有限データ上のプッシュダウンシステム {#the-story-is-a-pushdown-system}

物語は [`pushdown fn`](../concepts/kinds.md) で書きます。その中では次のことが成り立ちます。

- ローカル変数、引数、戻り値、物語変数の型はすべて [有限型](../concepts/kinds.md#finite-types) です。具体的には `bool`、`Int<lo, hi>`、列挙型、そして有限型からなる構造体、タプル、配列です。スタックフレームは戻り先と有限のローカル変数の組なので、スタックアルファベットは有限になります。これはプッシュダウンシステムの定義そのものです。
- `pushdown fn` から呼べるのは `pushdown fn` と `const fn` だけです。物語から呼ばれた `const fn` は、コンパイル時に定数へ畳み込まれるか、引数が実行時の有限型の値なら *表化* されます。表化では、引数のあらゆる組み合わせについてコンパイル時に評価します。これにより、物語が渡し得るどの入力でもエラーなく終了し、有限の結果を返すことが証明されます。
- 名前付きの関数は有限個しかないので、関数ポインタも有限の値です。物語の中のクロージャは第二級（渡して呼ぶことはできても、格納、返却、キャプチャはできない）なので、キャプチャした環境が状態に入り込むことはありません。
- 制御フローは構造化されています。`goto` はないため、制御が関数から出るのは呼び出しか戻りのときだけです。
- ループやシーン呼び出しの循環は、必ずステップを通らなければなりません。入力を待たずに動くコード（即時手続き）は再帰せず、定数で上限が決まらないループも持てません。そのため、入力と入力の間のコードは必ず終わります。

このモデルでは到達可能性が決定可能です。コンパイラは、すべての開始シーンと、その引数のすべての値から物語を漏れなく探索します。各シーンは入ったときの状態ごとに要約するので、多くの場所から同じ状態で呼ばれるシーンも、探索は 1 回で済みます。

### 演出は純粋で、読み返されない {#the-presentation-is-pure}

プレイヤーが目にする画面は [レンダー関数](../concepts/presentation.md) が計算します。レンダー関数は `const fn` で、チューリング完全ですが、純粋かつ決定的です。レンダーはステップの前の画面だけを受け取り、ステップのあとの画面を返します。レンダーから物語変数は読めず、物語から画面も読めません（`Screen` は有限型ではないからです）。したがって、物語がどの状態に到達するかに演出は影響しません。画面は、物語の解析で見つかった状態について、あとから計算すればよいのです。レンダーは純粋なので、コンパイラはそのステップに来得るすべての画面に対して、ただレンダーを実行します。

### チューリング完全なコードの入り口は開始シーンだけ {#only-through-entry-scenes}

ゲームシステムは普通の `fn` のコードで、`pushdown fn` を呼ぶことも、物語変数を読むこともできません。物語に入るには、有限型の引数を渡して [開始シーン](../concepts/entry.md) を起動するしかなく、解析はその引数が取り得るすべての値を対象にします。物語から戻ってくるのは、開始シーンの戻り値であるエンディングと、物語が書き込むだけで読み返さないメタデータだけです。システムが何を計算しようと、物語の動きは、コンパイラが解析済みの実行のどれかになります。

### 残る限界 {#where-limits-remain}

限界は 2 つ残ります。Kagari はそれを隠さず明示します。

- **レンダーはチューリング完全です。** あるステップで表示され得る画面の集合が有限に収まるかどうかは、一般には決定不能です。たとえば、ハブのループを通るたびにキャラクターを 10 ピクセルずつ動かすレンダーは、毎回新しい画面を生みます。*暫定：* コンパイラは画面の集合を不動点として計算し、あるステップの集合を上限（現在は 64 画面）を超えて増やすレンダーをエラーにします（`E5005`）。受理されたプログラムでは画面の集合が計算結果と完全に一致するので、この規則は健全です。ただし、上限より上でようやく有界になるレンダーは拒否されることがあります。また、`const fn` の評価にはどれも固定の予算があり、使い切るとコンパイルエラーになります（`E4003`）。
- **決定可能だからといって、安く済むとは限りません。** 状態の数は、互いに独立した物語変数の数に対して指数的に増えます。解析は状態数の上限（既定は 200 000。[プロジェクト](../tools/projects.md) で設定できます）に達すると止まり、警告 `W5006` を出します。それまでに見つかった問題は報告されますが、すべての状態を必要とする検査は省略されます。

## 制作者が得るもの {#what-studios-get}

以下の保証はどれも、ゲームのあらゆる実行、つまりすべての開始シーン、その引数のすべての値、すべての選択の並びについて成り立ちます。いずれも `kagari check` と `kagari build` が検査します。詳しくは [診断](../../diagnostics/index.md) の各章を参照してください。

| 保証 | コンパイラが検査すること | 診断 |
| ---- | ------------------------ | ---- |
| **ステップ間の停止性** | ループとシーン呼び出しの循環がすべてステップを通ること。即時手続きと、物語からの `const fn` 呼び出しが終了すること | `E5001`、`E5002`、`E3004`、`E3005`、`E4003` |
| **行き詰まる選択肢がない** | すべてのアームのガードが偽になる状態で到達する `choice!` がないこと | `E5003` |
| **使われない物語がない** | どの開始シーンからも到達しないシーン、どの状態からも到達しないステップ、物語に影響しない物語変数を報告 | `W5008`、`W5009`、`W5010` |
| **物語に実行時エラーがない** | 範囲外のインデックスなどのエラーを、物語がそこに行き当たる箇所で検出 | [定数評価](../../diagnostics/eval.md) |
| **画面の一貫性** | ステップが表示する画面が物語状態だけで決まり、どの経路から来たかに左右されないこと | `W5004` |
| **画面の有界性** | あるステップの画面の集合を際限なく増やすレンダーがないこと | `E5005` |
| **健全なゲームシステム** | すべてのモードが表示可能であること、プレイヤーを閉じ込めるオーバーレイがないこと、底のページから戻らないこと、モードのスタックが有界であること、すべてのエンディングを処理していること | `W6001`、`E6002`、`E6003`、`W6004`、`E2037` |

コンパイル時の検査だけでなく、このモデルは普通のエンジンでは実現できない性質をランタイムにももたらします。

- **壊れにくいセーブ。** [セーブ](../concepts/saves.md) は状態ではなくトレースを記録します。記録するのは、開始シーンとその引数、すべての選択の安定した ID、最後の選択からのステップ数、乱数のシードです。ロードではトレースを再生します。つまりセーブは、その位置に到達できることの *証拠* であり、到達できない位置のセーブは存在し得ません。スクリプトが変わっても、トレースが意味をなすかぎりセーブはロードできます。意味をなさなくなった場合は、解決できなくなった最初の選択でロードが止まり、それがどの選択かを示します。
- **決定的な再生。** Kagari には浮動小数点数がありません。物語の状態は有限型を使い、それ以外のコードは正確な整数、`Rat`、`Decimal` を使います。レンダーは純粋です。乱数はシード付きの生成器から得られ、そのシードはセーブに含まれます。解析では、乱数を引くたびに、取り得るすべての値へ分岐するものとして扱います。このため、同じトレースからは、どのマシンでも同じ物語状態と同じ画面が得られます。
- **高速なジャンプとプレビュー。** 物語状態と論理画面はトレースから決まるので、物語を再生すればどの位置でも再構築できます。ロードやバックログの巻き戻しは、すでにこの方法で動いています。演出を最初から再生する必要はありません。経路上の最後の [キーフレーム](../concepts/presentation.md) より前のレンダーは、画面に影響しないからです。*暫定：* 同じモデルで実現を見込んでいる、エディタのカーソル位置でのライブプレビューは、まだツールチェインに含まれていません。

## 制作者が手放すもの {#what-studios-give-up}

保証には代償があり、それを負うのは物語だけです。

- **物語で扱えるのは有限データだけ。** `pushdown fn` では Rust の整数、`String`、`Vec`、`Rat`、`Decimal` は使えません。カウンタには好感度 `Int<0, 5>` のような範囲付きの `Int<lo, hi>` を使い、複合代入は上下限で飽和します。
- **物語から外の世界は見えない。** 物語は `fn` を呼べないので、実行中に時計、ファイルシステム、画面、設定、メタデータを読めません。メタデータが物語に届くのは、開始引数として渡されたときだけです。
- **制御の制限。** シーンのループや再帰は、ステップを通らなければなりません。即時手続きのループは定数の範囲と配列に限られ、再帰もできません。`goto` はありません。
- **物語の中のクロージャは第二級。** クロージャを `pushdown fn` に渡して呼ぶことはできますが、格納、返却、キャプチャはできず、クロージャの中でステップを踏むこともできません。
- **演出は一方向。** ステップの表示内容を、そこまでの物語の経緯によって変えたいなら、その違いはレンダーを選ぶ物語変数として表す必要があります。画面から読み取ることはできません。
- **解析の予算には上限がある。** 表化される呼び出しには引数の定義域の上限、レンダーにはステップごとの画面数の上限、物語には状態数の上限があります。非常に大きな物語では、上限を引き上げる必要があるかもしれません。
- **保証を全体的に弱めてしまう言語機能は持たない。** 浮動小数点数、ユーザー定義のトレイト（標準ライブラリの固定されたトレイトだけがあります。ジェネリクスは使えます）、マクロはありません。[組み込み構文](../syntax/forms.md) は構文の一部として固定されています。

## 物語以外は自由に書ける理由 {#why-the-rest-of-the-game-stays-free}

こうした制限は、物語の外には一切かかりません。ゲームシステムは、言語の機能をすべて使える `fn` のコードです。Rust の整数、`String`、`Vec`、第一級のクロージャ、シグナル、再帰、非有界なループも使えます。その値をしらみつぶしに調べる解析はありません。ゲームシステムに対して行うのは、型検査と、モードグラフの検査だけです。モードグラフは、ソースに書かれた有限個のハンドラからコンパイラが集めます。ハンドラが無限ループしてもかまいません。システムが物語に影響を与えられるのは唯一の入り口を通じてだけなので、この章のどの保証もハンドラには依存しないからです。

演出もチューリング完全です。`const fn` ではループも再帰も、正確な数での計算もできます。純粋であり、しかもコンパイラが必要とする時点で入力が分かっているので、コンパイラは一般的な推論をする必要がなく、ただ実行すればよいのです。

結果として、役割がきれいに分かれます。正しさが作者の頭の中にある部分、つまり物語は、コンパイラが完全に検査できる部分です。それ以外は、すべて普通のプログラミングです。
