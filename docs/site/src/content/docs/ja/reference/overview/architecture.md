この章では Kagari の全体像を示します。ソースファイルが実行中のゲームになるまでの流れ、ゲームの各部分を何で書くか、各部分どうしがどうやりとりできるかを説明します。それぞれの要素の厳密な定義は後の章で行います。

## ソースから実行中のゲームまで {#from-source-to-running-game}

**プロジェクト。**ゲームは 1 つの [プロジェクト](../tools/projects.md) として管理します。プロジェクトとは、`kagari.toml` マニフェスト、`src/` 以下のソースファイル、`assets/` 以下のアセットを置いたディレクトリです。コンパイルはルートファイル（既定では `src/main.kis`）から始まり、`mod` 宣言をたどってほかのソースファイルをすべて読み込みます。ソースファイルには `.kis`（素の言語）と `.kix`（言語に `s!(…)` や `choice!{…}` などの [組み込み構文](../syntax/forms.md) を加えたもの）の 2 種類があります。拡張子で変わるのは使える構文だけで、意味は変わりません。アセットはソース中で `const BG_ROOF: ImageAsset = asset("bg/roof.png");` のような定数として名前を付けます。ファイルが実在するかどうかはコンパイラが検査します。

**ビルド。**[`kagari build`](../tools/cli.md) はプログラム全体をまとめてコンパイルします。すべてのファイルを構文解析して名前を解決し、型と [関数種別](../concepts/kinds.md) を検査し、定数とレンダーを評価し、物語とゲームシステムを解析してから、プログラムを生成します。エラーが 1 つでもあればビルドは止まりますが、警告では止まりません。出力先は `<out-dir>/<target>/` で、既定では `target/v0/` です。

| 出力 | 内容 |
| ---- | ---- |
| `game.kagari` | コンパイル済みのプログラム（物語、レンダー、ゲームシステム） |
| `*.kiarchive` | プログラムが参照するアセット。アセットディレクトリ直下のディレクトリごとに 1 つのアーカイブ、直下のファイルは `data.kiarchive`、ゲームが名前で指定するインストール済みフォントは `system-fonts.kiarchive`、使用する std のシェーダーは `std.kiarchive` |

[デバッグビルド](../tools/cli.md#build-profiles)では、デバッグツール用の `game.kagari-cache` も同じ場所に出力します。ビルドはこれらのファイルを書き出す前に、マニフェストに挙げたすべてのランタイムプロファイルが、参照されているすべてのアセットをデコードできるかを検査します。`kagari check` はビルド結果を書き出さずに同じ診断を報告します（保存するのは [解析キャッシュ](../tools/cli.md#the-analysis-cache) だけで、ソースが変わらないかぎり両方のコマンドがこれを使い回します）。言語サーバーは、入力に合わせて同じ診断を [エディタ](../tools/editors.md) に表示します。

ビルドではさらに、プログラムが使うすべてのシェーダーをその役割に照らして検証し、検証に通らないシェーダーがあれば失敗します。

**ランタイム。**[デスクトップランタイム](../tools/runtime.md) `kagari-desktop-runtime` は、ビルドしたゲームを Windows、macOS、Linux で動かします。ランタイムはゲームディレクトリから `game.kagari` を読み込みます。ゲームディレクトリは既定では実行ファイルのあるディレクトリなので、配布するゲームでは実行ファイルを `game.kagari` やアーカイブと同じ場所に置きます（macOS のアプリでは `Contents/Resources` に置きます）。読み込んだプログラムは、どこかを実行する前に検証します。そのうえで `fn main` を 1 回だけ実行してゲームシステムの記述を受け取り、開始ページを表示します。設定、メタデータ、セーブスロットは、ゲームディレクトリとは別のデータディレクトリに保存します。このランタイムが実装しているのはランタイムプロファイル `native_v0`、つまり標準ライブラリ全体です。[ヘッドレスモード](../tools/headless.md) を使うと、同じゲームをウィンドウなしでスクリプトどおりに動かせるので、自動テストに使えます。

## ゲームの各部分を書く種別 {#what-each-part-of-a-game-is-written-in}

ゲームは 3 つの部分からなり、部分ごとに決まった [種別](../concepts/kinds.md) の関数で書きます。

| 部分 | 種別 | 含まれるもの |
| ---- | ---- | -------- |
| 物語 | `pushdown fn` | シーン（`#[scene]`）、即時手続き、[物語変数](../concepts/story.md)（`static mut`）、プレイヤーが読んだり選んだりする [ステップ](../concepts/steps.md) |
| 演出 | `const fn` | 各ステップで画面を変える [レンダー関数](../concepts/presentation.md)、キャラクターの実例などの演出用補助関数、テキスト効果、定数 |
| ゲームシステム | `fn` | `fn main`、タイトルページ、メニュー、セーブ・ロードのページ、設定、バックログ、ゲーム画面など、物語の周りにあるものすべて |

型、定数、設定やメタデータ用の `static` ハンドル、アセット定数は、3 つの部分すべてで共有する普通のアイテムです。1 つのモジュールにどの種別を混ぜてもかまいません。種別はファイルではなく関数ごとに決まります。

<!-- diagram: architecture-layers (mermaid-ish)
flowchart TB
  system["ゲームシステム: fn (main、タイトル、メニュー、セーブとロード、設定、ゲーム画面)"]
  story["物語: pushdown fn (シーン、ステップ、選択肢、物語変数)"]
  pres["演出: const fn (レンダー、演出用の補助関数、テキスト効果、定数)"]
  system ==>|"開始シーンを起動: nav::start、有限型の引数"| story
  system <==>|"Narrative ハンドル: 入力、台詞、セーブ"| story
  story ==>|"エンディングの値、書き込み専用のメタデータ"| system
  story ==>|"ステップごとにレンダーを選ぶ"| pres
  pres -.->|"逆向きはない: レンダーは画面しか見ず、物語は画面を読まない"| story
  system ==>|"const fn を呼べる"| pres
-->
{{#include ../diagrams/architecture-layers.svg}}

どの矢印があり得るかは [呼び出し規則](../concepts/kinds.md#call-rules) で決まります。

- `fn` から呼べるのは `fn` と `const fn` です。`pushdown fn` は呼べず、物語変数も読めません。
- `pushdown fn` から呼べるのは `pushdown fn` と `const fn` で、`fn` は呼べません。実行時に扱う値はすべて [有限型](../concepts/kinds.md#finite-types) です。
- `const fn` から呼べるのは `const fn` だけです。物語変数、設定、メタデータなど、引数以外のものは一切読めません。

関数ポインタやクロージャの型にも種別が含まれるので、これらを経由してもこの規則は破れません。

## 入れ子になった 2 つの機械 {#two-nested-machines}

実行中のゲームは、入れ子になった 2 つの機械として動きます。

- 外側の**システム機械**は [モード](../concepts/system.md) のスタックを管理します。底にはタイトルやギャラリーなどのルートページかゲームモードがあり、その上に Config、Save、Backlog などのオーバーレイやダイアログが積まれます。入力を受け取るのは最上位のモードだけです。
- **ゲームモード**は実行中の物語、つまり [物語機械](../concepts/story.md) を 1 つ保持します。物語機械はプッシュダウン機械で、状態 σ はシーン内の位置、実行中のシーンと即時手続きのコールスタック、物語変数からなります。ゲームモードはこのほかに、現在の画面とプレイヤーの選択のトレースも保持します。

物語のコールスタックはゲームモードの中にあり、モードのスタックには載りません。そのため、セーブに含まれるのは実行中の物語だけで、周りのメニューは含まれません。セーブをロードしてもスタックに積むのではなく、ゲームモードが置き換わります。「ゲームが実行中」とは、スタックにゲームモードがあることにほかなりません。ゲームモードの上にオーバーレイやダイアログがある間は、物語は一時停止しています。

| 状態 | 寿命 | セーブに含まれるか |
| ---- | ---- | ------------------ |
| 設定 | 永続、大域的 | いいえ |
| メタデータ（解放状況、既読テキスト、閲覧済みの画像） | 永続、大域的 | いいえ |
| セーブスロット | 永続 | セーブそのもの |
| モードのスタックと各モードの状態 | ゲーム終了まで | いいえ |
| 実行中の物語（σ と画面） | 物語が終わるか、別の物語に置き換わるまで | はい（そこに至るトレースとして） |

## 部分どうしのやりとり {#how-the-parts-talk}

3 つの部分の間で、情報は一方向に流れます。何が起こるかを物語が決め、それがどう見えるかを演出が決め、その周りのすべてをゲームシステムが決めます。後段が自分の出力をどう使ったかを、前段が読み返すことはありません。

### 物語から演出へ {#from-the-story-to-the-presentation}

各ステップには、`s!(render = roof, …)` のように使うレンダーを指定します。物語がそのステップに着くと、エンジンは現在の画面にレンダーを適用し、結果を表示します。レンダーが受け取るのは画面だけなので、物語変数に左右されることはありません。逆に `Screen` は有限型ではないので、物語から画面は読めません。物語の展開によって演出を変えたいときは、分岐ごとに別のレンダーを渡し、物語の側で選びます。

### ゲームシステムと物語の間 {#between-the-game-system-and-the-story}

ゲームシステムと物語が接するのは、次の 4 か所だけです。

| 接点 | 方向 | やりとりするもの |
| ---- | ---- | -------- |
| [開始シーン](../concepts/entry.md) | システムから物語へ | `nav::start(entry, args, on_exit)` で、`#[entry]` シーンから有限型の引数を渡して物語を始めます。物語に入る方法はこれしかありません |
| [`Narrative` ハンドル](../concepts/system.md#the-narrative-handle) | 双方向 | ゲーム画面とゲームオーバーレイは、実行中の物語へのハンドルを受け取ります。これを使って現在の台詞、選択肢、バックログを表示し、物語を進める、アームを選ぶ、セーブする、巻き戻すといった操作をします。ハンドルから物語変数は読めません |
| [エンディング](../concepts/entry.md) | 物語からシステムへ | 開始シーンが戻ると、戻り値が終了ハンドラ `on_exit` に渡ります。終了ハンドラは起こり得るすべてのエンディングを処理しなければなりません |
| メタデータ | 物語からシステムへ | 物語は `Meta::write` でメタデータに書き込みますが、実行中に読み返すことはありません。システムはメタデータを読み、次の物語に開始引数として渡せます |

設定が物語に届くことはありません。設定によって表示を変えるレンダーは、設定値を読むのではなく、エンティティの表示を設定に連動させます。設定の適用は描画時にエンジンが行います。

## ゲームの実行の流れ {#a-run-of-a-game}

1. ランタイムは `game.kagari` を読み込んで検証し、`fn main` を実行します。そして、返された `System` レコードで指定された開始ページを表示します。
2. ページ、オーバーレイ、ダイアログはコンポーネント、すなわち UI を組み立てる素の `fn` です。ボタンのハンドラは `nav::call(Config)` や `nav::start(…)` などのナビゲーション関数を呼びます。
3. `nav::start` を呼ぶと、モードのスタックが新しいゲームモードに置き換わり、そこで開始シーンが動き始めます。
4. 物語は最初のステップまで一気に進みます。ステップのレンダーが画面を変え、ゲーム画面が台詞を表示し、物語は入力を待ちます。
5. プレイヤーの入力で物語が再開します。`s!` のステップなら先へ進め、`choice!` ならアームを選びます。物語は次のステップまで進みます。選択肢のたびに、エンジンが自動でセーブします。
6. 開始シーンが戻ると、終了ハンドラがエンディングを受け取り、たとえばクレジットへ遷移します。

[コンパイラの解析](./philosophy.md) は、手順 3〜6 を起こり得るすべての実行について調べます。すべての開始シーン、その引数のすべての値、すべての選択の並びが対象です。
