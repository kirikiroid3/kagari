Kagari のセーブはメモリの中身を書き出したものではありません。物語の開始からプレイヤーが行った
選択の記録で、ロードではその選択を再生します。この章では、セーブに含まれるもの、既存のセーブを
壊さずにパッチで変更できる範囲、そして再生が正確である理由を説明します。

## セーブは到達可能性の証拠 {#a-save-is-a-witness-of-reachability}

物語は [プッシュダウン機械](./story.md) で、入力はプレイヤーの選択と乱数生成器の抽選だけです。
開始シーンとその引数、乱数生成器のシード、選択の列がそろえば、物語の位置は一意に決まります。
セーブが記録するのはこの列（**トレース**）だけです。ロードでは開始シーンから物語を実行し直し、
記録した選択を順に与えて、セーブした位置まで進めます。

したがってセーブは状態そのものではなく、*その位置に到達できることの証拠*、言い換えれば開始から
の経路です。到達できない位置のセーブは作れません。また、物語自身が作り出せない物語変数の組み合わせが
ロードによって生じることもありません。そのため、コンパイラが物語に対して行う解析は、ロードした
ゲームでもすべて成り立ちます。

### 安定した選択肢 ID {#stable-choice-ids}

トレースには行番号もアームの位置も記録しません。選択はそれぞれ、次の三つの部分からなる
**選択肢 ID** として記録します。

| 部分 | 例 | 由来 |
| ---- | -- | ---- |
| `choice!` を含む関数のパス | `crate::story::Prologue` | モジュールツリーと関数名 |
| 選択肢の `id` | `confess` | `choice!` の `id = "…"` |
| 選ばれたアーム | `crate::story::Confess::Yes` | アームの値。列挙型のバリアントならそのパス、それ以外なら `#n`（アームの位置） |

たとえば `crate::story::Prologue/confess/crate::story::Confess::Yes` のようになります。呼び出しの
文脈は再生時に補われるため、関数があちこちから呼ばれたりループの中で実行されたりしても、選択肢の
`id` は関数の中で一意であれば足ります。アームの値には、自分で宣言した列挙型のバリアントを使って
ください。位置で記録したアームは、アームを並べ替えると壊れます。

## セーブの内容 {#what-a-save-contains}

| 部分 | 内容 |
| ---- | ---- |
| トレース | 開始シーンのパス、開始引数、PRNG のシード、すべての選択の選択肢 ID、最後の選択以降のステップ数 |
| 終了ハンドラ | `nav::start` に `on_exit` として渡した関数のパス |
| スクリプトハッシュ | セーブ作成時の `.kagari` ファイルの SHA-256 |
| スロット情報 | ローカル時刻、最後の行の話者と本文、画面の 320×180 のサムネイル |
| フォーマットのバージョン | セーブの構造のバージョン |

セーブにはシステムの状態を含みません。モードスタック、設定、メタデータはどれも入っていません
（[入れ子になった二つの機械](./system.md#two-nested-machines) を参照）。スロット情報は、セーブ
画面で `saves::info(slot)` と `ui::thumbnail(slot)` が表示するためのもので、ロードには使いません。

## ロードと食い違い {#loading-and-divergence}

`nav::load(slot)` はスロットを読み込み、実行中のプログラムでトレースを再生します。再生中、`s!`
ステップは自動で進みます。各 `choice!` では、記録した選択肢 ID と一致し、記録したアームを選べる
必要があります。トレースを使い切ったら、最後の選択以降に記録したステップ数だけ進めて止まります。
復元したゲームは、モードスタック全体と入れ替わります。

再生は表に何も出しません。既読フラグや既見集合を立てず、メタデータへの書き込みも繰り返さず、音も
鳴らさず、オートセーブもしません。復元したステップは、ステップに入るところからやり直します。
タイムラインが最初から始まるので、アニメーションもボイスももう一度再生されます。

セーブが現在のプログラムに合わなくなっていると、ロードは **食い違い**（`Divergence`）で止まります。
このとき `nav::load` はスタックを変えずに `Err(divergence)` を返し、`divergence.describe()` で
プレイヤー向けのメッセージが得られます。食い違いが起きるのは次の場合です。

| 原因 | メッセージの内容 |
| ---- | ---------------- |
| スロットが空、または範囲外 | スロットが空であること |
| ファイルを読めない、またはフォーマットのバージョンが未知 | セーブを読めないこと |
| 開始シーンがもう存在しない | 見つからない物語 |
| 開始引数が開始シーンの引数の型にもう合わない | 開始時の値が合わないこと |
| 物語が記録と別の選択肢にたどり着く | 期待した選択肢と実際の選択肢 |
| 記録したアームがない、またはそのガードが偽になった | 選択肢と、見つからないアーム |
| 記録した選択を使い切る前に物語が終わる | 残っている選択の数 |
| 最後の選択以降のステップが記録より少ない | 期待したステップ数と到達したステップ数 |
| 再生中に物語が実行時エラーで止まる | そのエラー |
| 1,000,000 ステップ以内に目的の位置に着かない | ステップ数の上限 |

クイックロードのバインディングは、食い違いをログに出すだけです。ロード画面では `describe()` で
表示します。

### パッチで変えてよいもの {#what-a-patch-may-change}

トレースに入っているのは選択肢 ID と最後のステップ数だけなので、たいていの編集ではセーブは
壊れません。編集箇所より *後ろ* の位置で作ったセーブへの影響は次のとおりです。

| 変更 | セーブへの影響 |
| ---- | -------------- |
| 本文の言い回し、話者、ボイス、テキスト効果の変更 | なし |
| レンダー、アセット、画面、アニメーション、音声の編集 | なし（画面は再生で作り直される） |
| 二つの選択肢の間にある `s!` ステップの追加・削除・並べ替え | なし |
| アームの値が列挙型のバリアントである選択肢での、アームの並べ替え | なし |
| 選択肢へのアームの追加 | なし |
| ゲームシステム（UI、モード、設定、バインディング）の変更 | なし |
| セーブ位置より手前で、最後の選択より後ろにある `s!` ステップの追加・削除 | 別の行で再開する。残りのステップが足りなければ食い違う |
| 選択肢を含む関数、その `id`、アームの列挙型やバリアントの名前変更・移動 | その選択肢で食い違う |
| アームの削除、または記録したアームを隠すガードの追加・変更 | その選択肢で食い違う |
| 物語の処理を変えた結果、先に別の選択肢に着く、または物語が早く終わる | 食い違う |
| 開始シーンの名前変更・移動、または引数の型の変更 | 食い違う |
| 位置で記録したアーム（`#n`）の並べ替え | 警告なしに別のアームが選ばれる |

物語変数やその初期値、条件を変えても、記録した選択が同じ選択肢をたどる限りは問題ありません。
たどれなくなった場合は、最初にずれた箇所を再生が報告します。

既読フラグ（既読スキップと、バックログでの既読表示に使います）はセーブとは別に保存し、
[ステップ ID](./steps.md#step-ids) で引きます。シーンごとに、既読ステップの範囲としてまとめて
記録します。関数の中でステップ（`s!` または `choice!`）を追加・削除すると、同じ関数でそれより
後ろにあるステップの既読フラグがすべてずれます。そのため、こうしたパッチを当てた後は、読んだはずの
行が未読になったり、その逆が起きたりします。ステップを含まないコードや、別の関数のステップには
影響しません。以前のバージョンの Kagari でビルドしたゲームの既読フラグは一度だけ破棄され、
該当する行はふたたび未読になります。

## スナップショットとトレース {#snapshots-and-traces}

トレースは **互換性の約束** です。スクリプトのバージョンが変わっても意味を保つのは、セーブの中で
この部分だけです。**スナップショット**（ある位置での物語の状態と論理画面）は、その位置に安く
たどり着くためのキャッシュにすぎません。プログラムが完全に同じであることが前提なので、スクリプト
ハッシュが一致するときだけ使います。スクリプトが違えば、エンジンはトレースを再生します。

*暫定:* 現在のエンジンはセーブにスナップショットを書き込みません。ロードも巻き戻しも、毎回物語の
先頭からトレースを再生します。スクリプトハッシュはすでに記録しており、現時点では一点だけに
影響します。クロージャで書いた終了ハンドラは同じスクリプトでしか復元できず、名前付きの関数は
パスで探します。

## 巻き戻し {#rewind}

`game.rewind(i)` は、実行中のゲームをバックログの `i` 番目の項目まで戻します。現在のトレースを
その項目で切り詰め、ロードと同じように再生します。メタデータは一切変わらず、既読フラグや既見集合も
立ったままです。

## セーブスロット {#save-slots}

スロットには `SaveSlot::Manual(k)`、`SaveSlot::Quick`、`SaveSlot::Auto(k)` の三種類があります。

- **手動** スロット `0..save_slots` には、セーブ画面から `game.save(slot)` で書き込みます。
- **クイック** スロットは、[バインディング](./system.md#bindings) の `QuickSave` と `QuickLoad`
  で書き込み・読み込みします。
- **オート** スロット `0..auto_slots` には、選択肢ステップに入るたびと終了時に、エンジンが
  スロットを順番に使い回しながら書き込みます。

設定した数を超える番号のスロットは無視されます。セーブしても何も起きず、読み込むと空として扱われます。
API の詳細は [`std::system::saves`](../../std/system-saves.md) を参照してください。

## 決定性 {#determinism}

選択と選択の間に物語が行う処理はすべて決定的です。だからこそ再生は正確になります。

- **乱数はシード付きで、記録されます。** シーンは `rng_choose::<T>()` で乱数を引きます。
  `nav::start` のたびに物語用の PRNG を新しいシードで初期化します。シードはトレースに、生成器の
  状態は物語の状態に含まれます。そのため再生ではすべての抽選が同じ結果になり、ロードし直して
  抽選を引き直すことはできません。
- **浮動小数点数はありません。** 言語にあるのは有界整数、Rust の整数、厳密な型 `Rat` と
  `Decimal` だけです（[数値](../syntax/numbers.md) を参照）。どの計算も、どのプラットフォームでも
  同じ結果になります。
- **レンダーは純粋です。** レンダーは直前の画面を受け取る `const fn` なので、選択を再生すれば同じ
  論理画面ができあがります（[レンダーは物語を見ない](./presentation.md#renders-are-blind-to-the-story)
  を参照）。
- **システムは物語に手を出せません。** 設定、メタデータ、シグナル、実時間が物語に入り込むことは
  ありません。メタデータが物語に届く経路は開始引数だけで、開始引数はトレースに記録されます。

物語を解析できるのも同じ仕組みのおかげです。コンパイラから見ると、乱数の抽選はプレイヤーの選択と
同じく、`T` の全値の中からの自由な選択です。

## プレビュー {#preview}

*予定:* 同じ仕組みは制作時のプレビューにも使えます。エディタであるステップへ移動するのは、
そこまでトレースを再生することと同じです。コストはキーフレームで抑えます。物語は先頭から
（スクリプトに変更がなければスナップショットから）再生しますが、レンダーは経路上の直近の
[キーフレーム](./presentation.md#keyframes) からだけ、アニメーションなしで実行します。
レンダーを編集しても、作り直しが必要なのは、現在の経路でそのレンダーが最初に使われた以降の画面だけです。
プレビュー用のツールはまだ提供していません。
